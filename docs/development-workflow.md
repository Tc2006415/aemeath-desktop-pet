# 开发流程与职责

## 工作原则

GitHub 是需求、决策和交付的记录；Codex 各任务是执行者。当前任务保持统筹职责。没有远程仓库之前先准备资料，远程仓库创建并推送初始提交之后再建立专题任务。

## 任务分工

| 任务 | 所有权 | 首项交付 |
| --- | --- | --- |
| 统筹（当前任务） | 产品范围、共享接口、ADR、集成和发布 | 需求基线、Issue 列表、PR 验收 |
| 桌宠程序 | 桌面窗口、动画播放、鼠标交互、设置和打包 | Windows 运行方案对比与最小可行性验证计划 |
| 像素动画 | 造型、动画帧、动作清单、素材格式 | 视频动作分段及像素素材规格提案 |
| Codex 联动 | 状态来源、适配器、事件去重和掉线处理 | 真实可用接口证据和模拟器边界 |
| 测试评审 | 验收场景、独立评审、回归和发布检查 | 可执行的验收矩阵 |

先完成资料与接口提案，再开始有依赖关系的实现。避免程序和素材各自决定图集格式。

## 阶段与验收

1. **M0 仓库与协作**：私有仓库、基础文档、任务分支、Issue 和 PR 模板；登录或权限缺失必须明确记录。
2. **M1 技术与接口**：确认内置皮肤或独立桌宠、Windows 技术栈、素材规格、状态事件协议；ADR 被接受。
3. **M2 桌宠 MVP**：可启动和退出、透明窗口、基础待机、拖动与恢复、缩放和位置持久化；动画可用 mock 状态触发，但须标记。
4. **M3 角色动画**：用户认可的游戏像素风格；待机、拖动、任务状态素材完整；逐项视觉验收。
5. **M4 联动**：真实来源驱动工作/等待/完成/失败；断连和过期事件有明确行为。接口不可用时，保留独立桌宠并说明限制。
6. **M5 发布**：干净环境启动、Windows 多显示器/DPI 验证、打包和版本说明；发布需明确用户授权。

## GitHub 流程

Issue 写清问题、范围、依赖和验收条件 → 独立 worktree/分支 → 实现与验证 → Draft PR → 独立评审 → 统筹合并 → 关闭 Issue。

每个 PR 尽量只有一个可独立验收的结果。未完成依赖的任务只写提案或测试设计，不把假接口当成已确定规范。保护规则和自动 CI 在技术栈确定后配置，不能把尚未配置的检查称为强制执行。

## 状态汇报

每次交付说明四项：完成了什么；证据在哪里；哪些尚未完成；下一任务可以依赖哪些文件或接口。遇到阻塞先记录具体原因，向统筹任务提出单一明确问题。
